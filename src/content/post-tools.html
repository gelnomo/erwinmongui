Architecture

Pick the tool your team can support, not the one on the shortlist.

During a large platform migration we chose Keycloak for single sign-on. It was a strong tool on paper, but it was new to the team and built on a stack we didn't know, and that piece of work took six times longer than planned. Here is what went wrong, the scorecard we used afterwards, and how AI assistants change the trade-off today.

By Erwin MonguiSeptember 21, 20267 min read
In short

For mission-critical systems like authentication, score every option on team familiarity, documentation, support and operational load, not only on features. Run a short, time-boxed proof of concept before you commit. AI assistants make unfamiliar tools easier to learn, but they don't remove the need for someone to own the tool in production.

What happened

At Fincaraiz we were moving a legacy ASP.NET monolith to Django and React microservices, for a platform with more than 5 million monthly visits. The old and new systems had to run side by side, so we needed one identity layer both could share. Keycloak was a sensible choice: open source, full-featured and widely used for single sign-on.

The problem was fit, not quality. Keycloak was new to the team and built on Java, which was outside our core skills. When integration issues appeared, nobody could dig into its internals with confidence, and the documentation had gaps for our exact setup. Every problem became an investigation. That part of the project took six times longer than estimated.

Why it happened

We evaluated the tool, not the fit. Our comparison of features was thorough. What we didn't ask was: when this breaks under real traffic, who on our team can fix it, how long will it take them, and where will they look for answers?

A tool is only as good as your team's ability to run it when it fails.

The scorecard we use now

After an open lessons-learned session, we added a vetting step for any mission-critical tool. Each option gets a simple score from 1 to 5 on these questions:

CriterionThe question to ask
Stack fitIs it built on a language and platform the team already knows?
Team experienceHas anyone on the team run it in production?
DocumentationDo the docs cover our exact use case, with working examples?
SupportIs there an active community, paid support, or both? How fast do issues get answered?
Operational loadWho patches, upgrades and monitors it, and how much time does that take each month?
Integration effortHow much custom code does it need to work with our systems?

A tool that scores low on stack fit and team experience can still win, but only if the plan includes the time and training to learn it, and a named owner.

Build, host or buy

For identity specifically, the options today fall into two groups, and the right choice depends on your team as much as your requirements:

  • Managed identity services such as Auth0, Okta, AWS Cognito or Microsoft Entra ID. You trade some flexibility and a monthly bill for far less to operate.
  • Self-hosted open source such as Keycloak. More control and no per-user licence, but your team runs it, upgrades it and secures it. Keycloak has become easier to operate in recent versions, but the ownership question doesn't go away.

In practice, the deciding factor is operational ownership. Self-hosting an identity provider means owning its availability targets and on-call rotation, security patching and CVE response, version upgrades, database backups, and signing-key rotation. If the team can't commit to that, a managed provider is the safer architecture choice.

How AI assistants change the trade-off

If we faced the same decision today, AI tools would help in three ways, and leave one problem untouched.

  • Learning an unfamiliar stack is faster. Assistants like Claude Code, Cursor or GitHub Copilot can explain an unfamiliar Java codebase, walk through configuration, and draft integration code. The "we don't know this language" penalty is smaller than it was.
  • Proofs of concept are cheaper. A working spike can often be built in days instead of weeks, so there is no excuse to skip one for a critical tool.
  • Documentation gaps are easier to bridge. An assistant can read the source code and the issue tracker when the docs fall short.
  • But ownership stays human. AI can help you set a tool up. It can't be on call for it, and for niche configuration it can be confidently wrong. For security-critical systems, every AI-suggested change still needs review by someone who understands it.

A simple process for your next decision

  1. Write down the requirements, including who will operate the tool.
  2. Shortlist two or three options, including at least one the team already knows.
  3. Score each option with the scorecard above.
  4. Run a time-boxed proof of concept on the top option, using AI assistants to move fast.
  5. Decide, name an owner, and record the reasons so the next team understands the choice.

How the team handled it

The overrun could easily have turned into blame. Instead, we treated it as a shared lesson and wrote the scorecard together. After that, people raised risks earlier, which was worth more than any single tool decision.
